## 修复的问题与流程缺口

### 健康检查继承 HTTP 代理

原镜像使用 urllib.request.urlopen 访问 127.0.0.1，会读取代理环境变量。实测：注入指向无效地址的 HTTP_PROXY，清空 NO_PROXY 后，原健康检查退出 1，错误为 Connection refused；同一容器实际服务正常，绕过代理的请求返回 HTTP 200。

Dockerfile 已将本地健康探测改为显式禁用代理。新的两份宝塔编排和旧目录挂载编排也覆盖相同探测，因此已导入的旧镜像无需为了这个修复重新上传。

验证工具新增 `--check-health-proxy`，对容器实际配置的健康检查注入代理干扰后执行。CI 增加这一回归检查和两份宝塔编排解析检查。

### 自动 CPU 回退无法处理 Docker 创建前失败

GPU 编排会先向 Docker 请求 GPU。驱动、Container Toolkit 或设备分配失败时，应用尚未启动，auto 模式没有机会回退 CPU。

新流程先使用不申请 GPU 的基础编排确认应用链路，再编辑同一个项目启用 GPU；项目名称、账号和数据卷保持一致。

### 短时检测与正式容器创建混用

前面的指导曾让用户把运行后即退出并自动删除的 GPU 检测命令放入宝塔“命令创建”。这种方式不能作为常驻应用部署的验收，也无法只凭面板“创建失败”判断 GPU 是否不可用。

新流程统一使用宝塔容器编排；诊断在 Ubuntu 宿主机终端收集具体容器状态、错误和日志。
